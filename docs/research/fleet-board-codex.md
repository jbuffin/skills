# Research: what Codex exposes for watching a task force

> *This was generated by AI. The findings come from probes an AI agent ran on the maintainer's machine.*

Answers #55 for the fleet board (#53). It builds on the Codex findings on #37 and ADR 0003: Codex teammates run as
`codex exec` (one process per turn) and are re-tasked with `codex exec resume`. No Codex driver is on `main` yet.

**Version:** `/opt/homebrew/bin/codex --version` → `codex-cli 0.162.0`. Probes ran on 2026-10-11 with the real binary (not the
cmux shim earlier on `PATH`), in a temp dir with a **throwaway `CODEX_HOME`** (only `auth.json` copied in) so the engineer's
hooks, sessions and state DBs were never touched. The model was `gpt-6-luna` at `model_reasoning_effort="low"`. The probe dir
wasn't a git repo because this agent's sandbox blocks git outside its worktree, so `--skip-git-repo-check` was passed. The
engineer's real `~/.codex` was only listed and read, with `sqlite3 -readonly` / `mode=ro`.

Labels: **Verified** = probe run, command and output given. **Doc** = official docs, linked. **Inferred** = not run.

## 1. Where the data lives (`CODEX_HOME`)

- **Verified:** with `CODEX_HOME=<tmp>`, one `codex exec` created everything under `<tmp>`: `sessions/YYYY/MM/DD/rollout-*.jsonl`,
  `state_5.sqlite`, `thread_history_1.sqlite`, `queue_1.sqlite`, `logs_2.sqlite`, `goals_1.sqlite`, `memories_1.sqlite`. Nothing
  went to `~/.codex`. So the board needs the list of `CODEX_HOME`s in use, the same as it needs every `CLAUDE_CONFIG_DIR`.
- **Doc:** "Codex stores its local state under `CODEX_HOME` (defaults to `~/.codex`)." ([config-advanced](https://learn.chatgpt.com/docs/config-file/config-advanced))
- **Verified:** `codex exec` didn't start the app-server daemon. Nothing was listening and no `app-server-control/` was created in the temp home.

## 2. Session listing

There is **no non-interactive CLI listing**. `codex --help` has no `sessions`/`list` subcommand. `codex resume` and `codex fork` open
a TUI picker (`--all` drops cwd filtering, `--include-non-interactive` adds exec sessions). `codex agents` is a TUI over daemon
threads only and exits with `stdin is not a terminal` (#37). Use these instead:

### 2a. `state_5.sqlite`, table `threads`: the index (Verified)

One row per thread, with `id`, `rollout_path`, `created_at[_ms]`, `updated_at[_ms]`, `source`, `thread_source`, `cwd`, `title`,
`first_user_message`, `preview`, `name`, `model`, `reasoning_effort`, `sandbox_policy`, `approval_mode`, `tokens_used`, `archived`,
`git_sha`, `git_branch`, `git_origin_url`, `cli_version`, `agent_nickname`, `agent_role`, `agent_path`, `originator`. Spawned
sub-agents also appear in `thread_spawn_edges(parent_thread_id, child_thread_id, status)`.

- The probe's exec thread got its row as soon as it started:
  `01a12dfc-…|exec|user||Run the shell command 'sleep 45; echo slept' once…|1791772917132|…/rollout-2026-10-11T22-41-53-01a12dfc-….jsonl|0`
  (`id|source|thread_source|name|title|updated_at_ms|rollout_path|archived`).
- `updated_at_ms` moved during the turn (it tracks rollout writes) and again at the end (`…2963704`).
- **`codex exec --thread-source <SOURCE>`** ("Source classification for newly created or forked threads") takes a free string.
  `--thread-source commodore` stored `thread_source = commodore` (row `01a12dfe-…|exec|commodore|…`). That's a native way to tag a
  teammate thread without writing a file, but the driver would have to pass it.
- In the engineer's real store, sources seen were `cli` (TUI, `originator codex-tui`), `vscode` (desktop app and IDE,
  `originator codex_work_desktop`), and JSON sub-agent sources like
  `{"subagent":{"thread_spawn":{"parent_thread_id":…,"agent_path":"/root/archive_html","agent_nickname":"Faraday",…}}}`.
- `name` is set only when a thread is renamed or titled. `session_index.jsonl` also maps `id` to `thread_name`. Exec threads had no name.
- **Caveat (Inferred):** this is an internal SQLite file (the `_N` suffix is a schema generation, and `codex features list` shows
  `sqlite  removed  true`). It isn't a documented interface and could be renamed in an update. The documented route to the same
  data is `thread/list` (2b).

### 2b. App-server `thread/list` and `thread/read` (Verified, stdio)

`codex app-server --listen stdio://` (the default transport, newline-delimited JSON-RPC) can be started by any process against a
`CODEX_HOME` and reads the stored threads. The probe client sent `initialize` → `initialized` → `thread/list` → `thread/loaded/list` →
`thread/read {includeTurns:true}`, and then exited. Results while the exec turn was **still running**:

```
list: {"id": "01a12dfc-…", "status": {"type": "notLoaded"}, "source": "exec", "cwd": "…/probe-dir", "name": null, "preview": "Run the shell command…", "updatedAt": 1791772917, …}
default list count: 0
loaded: {"data": [], "nextCursor": null}
read status: {"type": "notLoaded"}
turn: 01a12dfc-ef3e-… interrupted 1 items; …
```

- `thread/list` with no `sourceKinds` returns only `cli` and `vscode` threads. Exec threads need `sourceKinds:["exec",…]`. **Doc:**
  "When omitted or `[]`, the server defaults to interactive sources only: `cli` and `vscode`." ([app-server](https://learn.chatgpt.com/docs/app-server))
- **Status is only live for threads loaded in that same app-server process.** A thread run by `codex exec` (or by another app-server)
  shows `notLoaded`, and its in-progress turn was reported as **`interrupted`**, which is wrong while it's running. The board can't
  get a teammate's state from its own app-server.
- Schema (Verified, `codex app-server generate-json-schema --out <dir>`): `ThreadStatus` = `notLoaded | idle | systemError |
  active{activeFlags}`, `ThreadActiveFlag` = `waitingOnApproval | waitingOnUserInput`, `TurnStatus` = `completed | interrupted |
  failed | inProgress`, `ThreadSourceKind` = `cli | vscode | exec | appServer | subAgent | subAgentReview | subAgentCompact |
  subAgentThreadSpawn | subAgentOther | unknown`. `thread/status/changed` is "emitted whenever a loaded thread's runtime status changes" (Doc).

### 2c. Who hosts live threads (Verified, `pgrep`)

On this machine the desktop app (`/Applications/ChatGPT.app/…/codex … app-server --analytics-default-enabled`) and the VS Code
extension (`…/openai.chatgpt-…/codex … app-server`) each run **their own private app-server over stdio**. The shared daemon wasn't
running (`codex app-server daemon version` → `failed to connect to …/app-server-control/app-server-control.sock`). So the only
thread hosts an outside process can query for live status are the shared daemon (when it's running) and its own app-server.
Desktop, IDE and `codex exec` threads can only be read as stored data. **Inferred:** a daemon's `thread/list` would also report
exec threads as `notLoaded`, because it runs the same server code as the stdio probe. For daemon-hosted threads, #37 verified
`thread/read` → `status {"type":"active"}` then `{"type":"idle"}` over the daemon socket (WebSocket JSON-RPC on a Unix socket).

## 3. Turn state from files

### 3a. `thread_history_1.sqlite`: turns and items (Verified)

`thread_turns(thread_id, turn_id, status, started_at, completed_at, duration_ms, error_json, …)` and
`thread_items(thread_id, turn_id, item_id, item_type, item_json, created_at_ms, started_at_ms, completed_at_ms, …)`.

| Moment | `thread_turns` row | `thread_items` |
|---|---|---|
| 17 s into a running `sleep 45` | `…\|inProgress\|1791772913\|` | `userMessage` only |
| after normal exit | `…\|completed\|1791772913\|1791772963` | + `commandExecution` (917→962), `agentMessage` |
| `exec` killed with SIGTERM mid-command | stays **`inProgress`**, no `completed_at` | `userMessage` only |
| after `codex exec resume <id> "…"` | a second row on the same thread, `completed` | |

- `inProgress` means working only if the `codex exec` process is alive. A killed or crashed run leaves `inProgress` behind for good,
  so a reader must cross-check the process (`pgrep -f "codex exec"`, or a pid the driver keeps).
- Items are projected **when they complete**, so a long-running command isn't visible here until it ends. The engineer's real store
  shows the item types available: `agentMessage, reasoning, commandExecution, userMessage, mcpToolCall, fileChange, webSearch,
  imageView, subAgentActivity, sleep, collabAgentToolCall, imageGeneration, contextCompaction`, and turn statuses `completed`, `failed`.
- The SIGTERM also orphaned the tool's child shell (`/bin/zsh -c sleep 90…` and `sleep 90` kept running, and were killed by hand).
  The same thing happened on #37.

### 3b. Rollout JSONL (Verified)

`$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<local-time>-<thread_id>.jsonl`. Each line has `timestamp`, `ordinal` and `type`. The probe
turn wrote, in order: `session_meta`, `event_msg/task_started`, `response_item/message` ×4, `world_state`, `turn_context`,
`event_msg/item_completed (UserMessage)`, `response_item/custom_tool_call` (the command, written **when it starts**),
`token_usage_record`, `custom_tool_call_output` (a poll yield 30 s in), `custom_tool_call`, `event_msg/item_completed
(CommandExecution)`, `custom_tool_call_output`, `event_msg/item_completed (AgentMessage)`, `response_item/message`, `token_count`,
`event_msg/task_complete`.

- Working = the last `task_started` has no `task_complete` after it, **and** the process is alive (same caveat as 3a).
- Latest activity = the last `custom_tool_call` (its input is the shell command) or the last `item_completed`. The rollout shows a
  running command before SQLite does.
- Heartbeat = file mtime: writes came about every 30 s during a long command (as on #37).

### 3c. `codex exec --json` stdout (Verified)

`thread.started{thread_id}`, `turn.started`, `item.started{command_execution, command:"/bin/zsh -lc 'sleep 45; echo slept'"}`,
`item.completed`, `turn.completed{usage}`. This is the cleanest live activity feed, but only the launcher sees it. A board can read
it only if the driver saves it to a file in the run dir. That would be new output from the skills.

## 4. Push mechanisms: notify and hooks

### 4a. `notify` (Verified + Doc)

`notify = ["<program>"]` in `config.toml` runs the program with one JSON argument on `agent-turn-complete` (the only event, per
[config-advanced](https://learn.chatgpt.com/docs/config-file/config-advanced)). It fired for `codex exec`:

```
{"type":"agent-turn-complete","thread-id":"01a12dfc-…","turn-id":"01a12dfc-ef3e-…","cwd":"…/probe-dir","client":"codex_exec",
 "input-messages":["Run the shell command 'sleep 45; echo slept' once, then reply with exactly DONE."],"last-assistant-message":"DONE"}
```

It did **not** fire for the killed run. It's a single program per config (the engineer's is already used by the Computer Use client),
so the board can't add itself without changing the engineer's config.

### 4b. Hooks (Verified + Doc)

Twelve events ([hooks](https://learn.chatgpt.com/docs/hooks)): `SessionStart, SessionEnd, PreToolUse, PermissionRequest,
PostToolUse, PreCompact, PostCompact, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt`. They're configured in
`hooks.json` or inline `[hooks]` at user level (`$CODEX_HOME`) or project level (`<repo>/.codex/`, loaded only when the project is
trusted). Non-managed hooks must be trusted (by hash, through `/hooks`) unless run with `--dangerously-bypass-hook-trust`.

- **Verified, hooks do fire in `codex exec`:** the normal run logged `SessionStart{source:"startup"}` → `UserPromptSubmit` →
  `PreToolUse{tool_name:"Bash"}` → `PostToolUse` → `Stop{last_assistant_message:"DONE"}` → `SessionEnd{reason:"other"}`. The resume
  logged `SessionStart{source:"resume"}` … `SessionEnd`. Every payload had `session_id`, `transcript_path`, `cwd`, `hook_event_name`,
  and (except SessionEnd) `model`, `permission_mode`, plus `turn_id` on turn events.
- **Verified, killed run:** only `SessionStart`, `UserPromptSubmit`, `PreToolUse`. No `Stop`/`SessionEnd`, so hooks can't detect a crash.
- `codex exec` warned that SessionEnd and Interrupt hook timeouts are clamped to 3 s.
- The engineer already has user-level hooks (`~/.codex/hooks.json`) from cmux and herdr feeding their own UIs. That shows the
  pattern works, and also that any hook the board added would run for **every** Codex session, not just task forces. It's new
  config, not native data.

## 5. Waiting on the engineer (needs-input)

- **Verified (#37):** `codex exec` threads record `approval_policy "never"`. Denied actions return to the model, and nothing
  prompts, so a Codex teammate under the current driver can never be waiting on input. Between turns it's simply idle (process exited).
- **Doc/Schema:** a loaded thread's `active.activeFlags` carries `waitingOnApproval` / `waitingOnUserInput`, and the
  `PermissionRequest` hook fires on approval prompts. Both apply only to interactive or daemon threads. A board would see the flag
  only for threads on the shared daemon. **Not probed** here, because it needs the daemon, which self-updates and leaves processes
  behind (#37, ADR 0003).

## 6. Opening or resuming a session from another app

- **Verified (help + #37):** `codex resume <id|name> [PROMPT]` opens the TUI on a thread (UUID or session name, `--all` /
  `--include-non-interactive` in the picker). `codex exec resume <id> "<prompt>"` re-tasks headless. It runs in the current
  directory and needs the sandbox passed again (`-c sandbox_mode=…`, #37/ADR 0003). The probe resumed the exec thread this way and
  got a second `completed` turn. `codex fork` copies a thread into a new one. `codex resume --remote unix://` attaches the TUI to a
  daemon thread.
- **Verified:** the desktop app registers the `codex` URL scheme (`plutil -extract CFBundleURLTypes … /Applications/ChatGPT.app/Contents/Info.plist`
  → `["codex","http","https"]`). **Doc:** `codex://threads/<thread-id>` opens "a local chat" ([app commands](https://learn.chatgpt.com/docs/app/commands)).
  Whether it opens an exec-created thread isn't documented, and it wasn't tried, so the engineer's desktop app was left alone.
- Opening someone else's live `codex exec` mid-turn isn't possible. There's no attach, only resume after it exits.

## What this means for the fleet board

A Codex teammate is a thread id plus a `codex exec` process. With the thread id (the session-id column of `teammates.tsv`, once a Codex driver writes it) and the right
`CODEX_HOME`, the board can read most of a teammate line from Codex's own stores, read-only:

| Board field | Codex native source | Verdict |
|---|---|---|
| Run: repo | `threads.cwd`, `git_origin_url`, `git_branch` | **Yes**, per thread (the run dir is still the better source) |
| Run: mission, mode, current unit | none | **No**, Codex has no concept. Comes from the run's own files (`state.md`, `team.env`) |
| Run: needs-input | none for exec threads (`approval "never"`) | **No** natively. Only daemon/interactive threads have `waitingOnApproval`/`waitingOnUserInput` |
| Teammate: name | `threads.name` is empty for exec; `--thread-source` can tag | **No** natively. Map thread id → name via `teammates.tsv` |
| Teammate: role | `agent_role` only for in-session sub-agents | **No**, comes from `teammates.tsv` |
| Teammate: unit | none | **No**, comes from the run's files |
| Teammate: state | `thread_turns.status` (`inProgress`/`completed`/`failed`) or rollout `task_started`/`task_complete`, **plus process liveness** | **Yes, with a cross-check.** `inProgress` + process alive = working; last turn `completed` = idle/done between turns; `inProgress` + no process = died. App-server `thread/read` is **not** usable (exec threads show `notLoaded` and a running turn shows `interrupted`) |
| Teammate: time in state | `thread_turns.started_at` / `completed_at` | **Yes** |
| Teammate: latest activity | rollout's last `custom_tool_call` (running command) or last `item_completed`; `thread_items` once an item finishes; mtime/`updated_at_ms` as a heartbeat | **Yes**, with a parser for the rollout or SQLite |

Gaps and risks:

- `state_5.sqlite` and `thread_history_1.sqlite` are undocumented internals with versioned names. The rollout JSONL is the steadier
  on-disk format, and `thread/list` over a stdio app-server is the documented one (it gives index data, not live state).
- Hooks and `notify` would give push updates, but they're new config that applies to every Codex session. They're optional, not needed.
- Things the skills might add, smallest first: pass `--thread-source commodore` (or a per-run tag) so the board can find task-force
  threads without `teammates.tsv`. Record the exec pid if the driver doesn't already, so a crash can be told from a running turn.
  Optionally tee `--json` to the run dir.
