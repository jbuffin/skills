# Fleet board research: what Copilot CLI exposes for watching a task force

> *This was generated by AI. The findings come from probes an AI agent ran on the maintainer's machine.*

Answers [#56](https://github.com/jbuffin/skills/issues/56) for the fleet board map ([#53](https://github.com/jbuffin/skills/issues/53)).
Builds on the Copilot findings in [#37](https://github.com/jbuffin/skills/issues/37) (liveness, resume by name,
`--session-id`, `COPILOT_AGENT_SESSION_ID`).

**Version:** `copilot --version` → `GitHub Copilot CLI 1.0.95.` (macOS, darwin-arm64), 2026-10-11.

**Labels:** **Verified** = a command was run and its output is quoted. **Doc** = official docs or CLI help text,
linked or named. **Inferred** = reasoning from the above, not probed.

**Method:** read-only listing of `~/.copilot/session-state/` (85 sessions) and `~/.copilot/session-store.db`
(`sqlite3 -readonly`). Three throwaway `-p` sessions in temp git repos, run under `env -i`, with
`--model gpt-5-mini --reasoning-effort low --available-tools bash view edit create glob grep --no-ask-user`.
Nothing of the engineer's was resumed, messaged or deleted. Probe sessions, logs and repos were deleted afterwards.

## 1. Session listing

There is **no CLI command that lists sessions**. An outside process lists them from disk.

- **Doc/Verified:** `copilot sessions --help` has one subcommand, `import`. `copilot --resume` with no value opens an
  interactive picker only.
- **Doc:** state lives under `COPILOT_HOME` (default `$HOME/.copilot`; `copilot help environment`). The board must
  honour `COPILOT_HOME` the same way it honours several Claude config dirs.
- **Verified:** one directory per session, `~/.copilot/session-state/<uuid>/`, holding `workspace.yaml`,
  `events.jsonl`, `checkpoints/`, `files/`, `research/`, `rewind-file-snapshots/`, sometimes `session.db`, and while
  a process holds it `inuse.<pid>.lock` + `inuse.<pid>.hold`. The SDK docs name the same directory
  ([session persistence](https://docs.github.com/en/copilot/how-tos/copilot-sdk/use-copilot-sdk/session-persistence)).
- **Verified:** `workspace.yaml` for a probe launched with `--session-id <uuid> -n fleetprobe-implementer`:

  ```yaml
  id: c7d43cc1-2505-4080-a1c8-66db1d5dd7e9
  cwd: …/probe/repo
  git_root: …/probe/repo
  branch: main
  client_name: github/cli
  name: fleetprobe-implementer
  user_named: true
  created_at: 2026-10-12T02:41:56.452Z
  updated_at: 2026-10-12T02:41:56.497Z
  ```

  Real sessions also carry `repository: owner/name` when the repo has a GitHub remote. Without `-n`, `name` is an
  auto-generated title (`'Review PR #1734 for Merge'`, `user_named: false`). So `-n <teammate>` gives the board the
  teammate name, and `cwd` gives the worktree (which maps to the unit through `worktrees.tsv`).
- **Verified:** `~/.copilot/session-store.db` (SQLite) has a `sessions` table (`id, cwd, repository, host_type,
  branch, summary, created_at, updated_at`) and a `turns` table (`session_id, turn_index, user_message,
  assistant_response, timestamp`). `summary` was the first prompt; the `-n` name is **not** stored there. It's an
  undocumented internal index: useful for a quick filter by `cwd`/`repository`, not something to depend on.
- **Verified:** `~/.copilot/open-sessions-state.json` maps a few session ids to `{openedAt, refreshedAt, working}`.
  None of the `-p` probe sessions appeared in it. **Inferred:** it's written by interactive or app clients, not
  `-p`, so it can't serve as the list of live teammates.
- **Live or not — Verified:** a session is live when `inuse.<pid>.lock` exists **and** `kill -0 <pid>` succeeds.
  The probe's lock files appeared within 6 s of launch and were removed at normal exit. #37 showed they're left
  behind after `kill -9`, so the PID check is required.

## 2. `events.jsonl`

- **Location — Verified:** `$COPILOT_HOME/session-state/<uuid>/events.jsonl`, append-only JSONL. Each line is
  `{type, data, id, parentId, timestamp}` (subagent events add `agentId`). The `agentStop` hook payload hands over
  the same path as `transcriptPath`. **Doc:** the format isn't documented; the SDK docs don't mention the file, so
  the schema can change between releases.
- **Event types — Verified** (counts across 85 local sessions, CLI versions up to 1.0.95): `tool.execution_start`,
  `tool.execution_complete`, `assistant.message`, `assistant.turn_start`, `assistant.turn_end`, `hook.start`,
  `hook.end`, `permission.requested`, `permission.completed`, `user.message`, `session.usage_record`,
  `system.message`, `session.shutdown`, `session.resume`, `session.start`, `model.*` (call/turn bookkeeping),
  `session.usage_checkpoint`, `session.mode_changed`, `session.compaction_start`/`_complete`,
  `session.task_complete`, `session.binary_asset`, `session.model_change`, `human_response.recorded`,
  `skill.invoked`, `subagent.started`/`completed`/`configured`/`selected`/`deselected`,
  `session.permissions_changed`, `system.notification`, `session.info`, `session.auto_mode_resolved`,
  `session.plan_changed`, `abort`, `session.workspace_file_changed`, `session.context_changed`, `session.error`.
- **Useful fields — Verified:**
  - `session.start.data`: `sessionId`, `copilotVersion`, `selectedModel`, `reasoningEffort`, `remoteSteerable`,
    `alreadyInUse`, `context {cwd, gitRoot, repository, branch, headCommit, baseCommit}`.
  - `session.resume.data`: same `context`, `alreadyInUse`, `selectedModel`.
  - `user.message.data`: `content` (the prompt, so the task a teammate was given), `delivery`
    (`idle` | `queued` | `steering`), `agentMode`.
  - `tool.execution_start.data`: `toolName`, `arguments` (for `bash`, `command` and `description`), `toolTitle`.
  - `assistant.message.data.content`: the model's text.
  - `session.task_complete.data`: `{success, summary}`, e.g. `"Approved and squash-merged #1708, #1710, #1711 …"`.
  - `session.mode_changed.data`: `previousMode`/`newMode` (`interactive`, `plan`, `autopilot`).
  - `session.shutdown.data.shutdownType`: only `routine` seen (313 of 313).
  - `system.notification.data.kind.type`: `agent_idle` (a subagent went idle), `shell_completed`,
    `shell_detached_completed`.

### What marks working, waiting and done

Derived from the last event in the file, read together with the PID check from section 1.

| State | Last event(s) | Evidence |
| --- | --- | --- |
| Thinking (model call) | `assistant.turn_start` or `user.message`, no `assistant.message` yet | **Verified:** probe sampled `last=assistant.turn_start` from t+6 s to t+15 s while the model ran |
| In a tool | `tool.execution_start` (or its `hook.end` for `preToolUse`) with no `tool.execution_complete` for that `toolCallId` | **Verified:** `last=hook.end` for the whole 20 s `sleep`; #37 saw the same for 50 s |
| Needs input: permission | `permission.requested` with no `permission.completed` for its `requestId` | **Verified** pairs in history: 2003 requested / 1995 completed; `decisionSource` `human_response` when a person answered |
| Needs input: question | `tool.execution_start` with `toolName: "ask_user"`, then `human_response.recorded` when answered | **Verified** in history: ask at `04:26:47.006Z`, answer recorded `04:26:51.222Z` |
| Idle, waiting for next prompt (interactive) | `assistant.turn_end`, process alive | **Inferred** from history: the next event is `user.message` with `delivery: "idle"` |
| Done (`-p` run) | `session.task_complete` and/or `assistant.turn_end`, then `session.shutdown`; process gone | **Verified:** probe ended `assistant.turn_end → hook (agentStop, sessionEnd) → session.usage_checkpoint → session.shutdown`; locks removed |

Caveats:

- **Verified:** a `-p` teammate with `--no-ask-user` never waits: unmatched permission requests are auto-denied
  (#37; history shows `denied-no-approval-rule-and-could-not-request-from-user` with `decisionSource:
  unattended_fallback`). "Needs input" only happens in interactive sessions, which in a task force usually means
  the coordinator.
- **Verified:** nothing is written while a model call or tool call runs (silent 9 s+ during the model call, 20 s
  during the tool call), so file mtime is not a "stuck" signal.
- **Verified (probe 2):** a second process can resume a session that's already running. `copilot --resume <id> -p …`
  12 s into a running teammate succeeded (`session.resume` with `alreadyInUse: true`), both processes appended to
  the same `events.jsonl`, and the second wrote `session.shutdown` while the first was still running. So
  "last event is `session.shutdown`" doesn't prove the teammate is done; the PID/lock check decides.
- `-p --output-format json` stdout carries extra ephemeral events that are **not** in `events.jsonl`, notably
  `assistant.idle`, `session.background_tasks_changed` and a final `result {exitCode, usage}` (**Verified**). Only
  the launcher owns that stream, so the board can't use it without the driver saving it.

## 3. Hooks

- **Doc** ([CLI hooks reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-hooks-reference)):
  events `sessionStart`, `sessionEnd`, `userPromptSubmitted`, `userPromptTransformed`, `preToolUse`, `postToolUse`,
  `postToolUseFailure`, `agentStop`, `subagentStart`, `subagentStop`, `errorOccurred`, `preCompact`,
  `notification`, `permissionRequest`. Every payload carries `sessionId`, `timestamp`, `cwd`.
  `notification_type` is one of `shell_completed`, `shell_detached_completed`, `agent_completed`, `agent_idle`,
  `permission_prompt`, `elicitation_dialog`; `notification` is async and never blocks. `sessionEnd.reason` is
  `complete | error | abort | timeout | user_exit`.
- **Doc:** loaded from the repo (`.github/hooks/*.json`, inline `hooks` in `.github/copilot/settings.json` /
  `settings.local.json`, and also `.claude/settings.json`), the user (`~/.copilot/hooks/*.json`, inline `hooks` in
  `~/.copilot/settings.json`), policy dirs and plugins.
- **Verified, repo hooks fire in `-p` mode, but only in a trusted folder.** A repo with `.github/hooks/probe.json`
  logging every payload: under `/private/tmp` (not in `trustedFolders`) nothing fired. The same repo under `$HOME`
  (trusted on this machine) logged `userPromptSubmitted`, `sessionStart {source:"new"}`, `preToolUse
  {toolName:"bash"}`, `postToolUse`, `agentStop {stopReason:"end_turn", transcriptPath}`, `sessionEnd
  {reason:"complete"}`. User-level hooks fired in both.
- **Verified:** every hook run is also recorded in `events.jsonl` as `hook.start {hookType, input}` / `hook.end
  {success}`. Over the local history the `notification` inputs carried `notificationType` `permission_prompt`
  (281), `elicitation_dialog` (72), `shell_completed` (11) and `agent_idle` (10). These events only exist when some
  hook is configured, so they're a by-product, not a guaranteed signal.
- **Verified, prior art on this machine:** `~/.copilot/settings.json` already has cmux hooks on `SessionStart`,
  `PreToolUse`, `Notification`, `Stop` and `SessionEnd` (they call `cmux hooks feed/enqueue copilot …`), and herdr
  installed `~/.copilot/hooks/herdr-agent-state.sh` on `SessionStart`. Terminal multiplexers already use hooks as
  their state feed. **Inferred:** a fleet-board hook would work the same way, but it is new config for the engineer
  to install, so by the map's rule it's a fallback, not phase 1. `events.jsonl` already holds everything the hooks
  would report.

## 4. Opening or resuming a session from another app

- **Doc/Verified:** `copilot --resume <id | 7+ char prefix | name>` or `copilot --session-id <uuid>` opens it.
  Names are case-insensitive and not unique (#37). From another app: open a terminal at the session's `cwd` and run
  `copilot --resume=<id>` (interactive) — the `-p` summary already prints `Resume copilot --resume=<id>`.
- **Verified:** resuming a session that another process is still running is **not refused** (probe 2). An "Open"
  button on the board that runs `copilot --resume` against a live teammate would start a second writer on the same
  session. The board should check the `inuse.<pid>.lock` PID first and only offer resume for sessions that aren't
  live.
- **Doc (`copilot --help`):** `--remote` / `/remote on` lets GitHub web, mobile and VS Code steer a running
  session ([changelog, GA 2026-05-18](https://github.blog/changelog/2026-05-18-remote-control-for-copilot-cli-sessions-now-generally-available-on-mobile-web-and-vs-code/),
  [preview 2026-04-13](https://github.blog/changelog/2026-04-13-remote-control-cli-sessions-on-web-and-mobile-in-public-preview/)).
  `--connect [<sessionId>]` connects to a remote session; `--acp` runs Copilot as an Agent Client Protocol server;
  `copilot app` opens the GitHub Copilot desktop app. `session.start.data.remoteSteerable` records whether a session
  was started remote-steerable (`false` for the probes). Not probed. **Inferred:** `--remote` is the native route to
  the later phone/messaging goals, at the cost of routing through GitHub.
- **Doc:** the Copilot SDK can `listSessions()` (filter by repository) and `resumeSession(id)`
  ([session persistence](https://docs.github.com/en/copilot/how-tos/copilot-sdk/use-copilot-sdk/session-persistence)).
  Resuming isn't read-only, so it doesn't suit the board.
- **Doc:** OpenTelemetry export (`copilot help monitoring`): `COPILOT_OTEL_FILE_EXPORTER_PATH` writes spans
  (`invoke_agent`, `chat <model>`, `execute_tool <tool>`) and metrics as JSONL. It must be set in the teammate's
  environment at launch, so it's a driver change, not a native feed. Not probed.

## What this means for the fleet board

Copilot CLI has no live-session API or listing command, but a read-only scan of `$COPILOT_HOME/session-state/*/`
(`workspace.yaml` + `inuse.<pid>.lock` + `kill -0` + the tail of `events.jsonl`) gives most per-teammate fields
without any hook or skill change.

| Field | From Copilot natively? | Source |
| --- | --- | --- |
| **Run:** repo | Yes | `workspace.yaml` `repository` / `git_root`, `session.start.context` |
| **Run:** mission | No | Only in commodore's run files (`state.md`); the coordinator's first `user.message` is a weak proxy |
| **Run:** mode | No (commodore's mode) | Copilot's own `session.mode_changed` (`interactive`/`plan`/`autopilot`) is a different thing |
| **Run:** current unit | No | Run files; Copilot only knows each session's `cwd`/`branch` |
| **Run:** needs-input | Yes, for interactive sessions | Unanswered `permission.requested`, or `ask_user` with no `human_response.recorded`. `-p` teammates never wait |
| **Teammate:** name | Yes, if launched with `-n <name>` | `workspace.yaml` `name` (`user_named: true`) |
| **Teammate:** role | No | `teammates.tsv` / the prompt file; not in Copilot's state (a `--agent <role>` launch would be visible only in `subagent.*`/config, not probed) |
| **Teammate:** unit | Partly | `cwd`/`branch` → unit through `worktrees.tsv` |
| **Teammate:** state | Yes | PID-checked lock + last event (table in section 2) |
| **Teammate:** time in state | Yes | `timestamp` of the event that entered the state; file mtime is not reliable mid-call |
| **Teammate:** latest activity | Yes | Last `tool.execution_start` (`toolName`, bash `description`/`command`), `assistant.message.content`, or `session.task_complete.summary` |

Gaps and cautions for the spec:

- The board needs the team dir's files to group sessions into a task force and to supply mission, mode, current unit
  and role. Joining is easiest by session id: a Copilot driver that launches with `--session-id <uuid> -n <name>`
  (the #37 recommendation) and records the uuid in `teammates.tsv` needs nothing new for the board.
- `events.jsonl` is undocumented and its event names can change between releases; pin the parser to tolerant
  matching and show the CLI version (`session.start.copilotVersion`).
- Always decide "live" from the PID in `inuse.<pid>.lock`, never from the last event alone, because concurrent
  resumes write `session.shutdown` into a session that's still running.
- Don't offer "resume" on a live session; it isn't refused and creates a second writer.
- Hooks (repo or user) are a working push alternative, but they need the folder trusted and new config installed,
  so they're out of phase 1 by the harness-native-first rule.
